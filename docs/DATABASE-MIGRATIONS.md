# 数据库迁移与发布

## 支持范围

当前迁移链为 `bf244f9a8b76 → e7cc9aa08769 → 8946c48f5315`。

- 空数据库从基线安装；已有数据库只支持从 `v0.1.4` 的发布边界 `bf244f9a8b76` 升级。
- 早于该边界的已发布数据库，应先使用相应旧版本代码升级到 `bf244f9a8b76`，再切换到当前版本。
- 曾运行被压缩的开发迁移的数据库不在自动升级范围。必须核对结构和数据，选择备份后重建或经审查的专项转换；不能仅修改版本号。
- 执行升级前备份数据库并运行 `alembic current`，确认版本属于上述支持路径。不要对用户数据库执行未经验证的 `stamp head`。

## 安装与升级

```bash
alembic current
alembic upgrade head
alembic current
```

`bf244f9a8b76` 保存发布边界的完整结构；`e7cc9aa08769` 汇总尚未发布的结构变更；`8946c48f5315` 补回管理员角色名称及过期操作诊断的数据修复。保留自定义角色名称，不改变角色成员或权限。

压缩迁移必须保留手写 SQL，尤其是平台审计追加限制、审计关联验证、平台主体和租户安全版本触发器。SQLAlchemy 的结构自动对比不会自动生成这些保护。

## 回滚

回滚前停止写入并备份数据。迁移的 downgrade 会移除新表或新字段，不能代替数据恢复；优先使用经过演练的数据库备份与匹配的应用版本恢复。隔离测试中空库的 downgrade 成功，不表示带业务数据的降级是无损的。

## 发布规则

1. 开发分支内尚未发布的迁移可以合并；发布后的迁移冻结，后续修复追加新迁移。
2. 每个版本尽量保持少量职责明确的迁移，不以文件数量替代升级正确性。
3. 发布前验证空库安装、受支持版本升级、数据修复及数据库安全保护；记录唯一 head。
4. 不提交实验数据库快照、备份迁移目录、临时操作脚本或本地凭据。

## 决策记录

1. **保留发布边界版本号** — 当前压缩支持 `v0.1.4` 边界和空库；更早版本先沿旧发布链升级。**反例**: 直接将任意旧数据库标记为新 head 会遗漏结构和数据变更。**回归**: `tests/test_release_migration_roundtrip.py`。
2. **显式保留数据库安全触发器** — 结构压缩不能削弱数据库强制的审计和撤权机制。**反例**: 仅提交自动生成的表结构，新安装没有审计追加限制或安全版本更新。**回归**: `test_fresh_install_preserves_security_triggers`。
3. **迁移失败即停止初始化** — 初始化脚本不得在升级失败后自动 `stamp head` 或继续运行种子脚本。**反例**: 不兼容的旧数据库被标成最新，后续运行缺表或缺列。**回归**: `tests/scripts/test_init_migration_failure.py`。
4. **保留默认租户模型授权回填** — 按原迁移为已启用模型建立默认租户策略，按 `sort_order/model_id` 确定默认模型，停用模型不授权。**反例**: 只创建空策略表会让已有部署升级后失去可用模型。**回归**: `test_release_boundary_data_survives_upgrade`。
5. **保留存量菜单和登录审计转换** — 建立父菜单外键前将根节点的 `0` 转成 `NULL`；可确定用户归属的登录记录回填租户，未知失败保持 unresolved。**反例**: 根菜单导致升级外键失败，或历史登录记录无法按租户查询。**回归**: `test_release_boundary_data_survives_upgrade`。
