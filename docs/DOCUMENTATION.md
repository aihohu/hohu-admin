# 文档维护与公开范围

`docs/` 维护随代码版本保存的贡献、安全、架构、迁移与发布约束。使用、部署和二次开发教程统一在 `hohu-admin-docs` 维护，本仓库旧教程只保留链接入口。同一正文不在两边复制。

## 收录标准

- 说明读者、适用范围、前提条件、操作步骤和已知限制。
- 使用仓库内可核对的命令、配置和接口；区分当前能力与尚未实现的方案。
- 一个主题只有一个维护来源，其他文档通过链接引用。API 字段细节优先由运行服务的 OpenAPI 提供。
- 示例不包含真实账号、令牌、业务数据、本机绝对路径或未验证的服务承诺。
- 功能变更时同步更新对应手册。架构背景、备选方案和讨论过程默认内部维护；影响使用、扩展和升级的稳定结论整理到正式手册。
- 新文档需加入 [文档入口](README.md) 和 `public-docs.txt`，并通过文档检查；通过链接检查不等于通过内容评审。

## 开发过程资料

草案、实现计划、调试笔记、测试报告、提示词、原型及临时附件保存在被忽略的 `.local/docs/`，按 `specs/`、`plans/`、`reports/` 等分类。此目录适合个人临时工作，不能成为团队唯一知识库。需要长期协作的内部资料通过私有仓库或受控文档空间维护；对外评审使用经整理的公开提案或摘要，不直接发布原始内部记录。

Spec-First 仍然有效：先写设计，再实现，再把已经落地的行为、接口契约、权限边界、兼容性和已知限制整理进正式手册。原始 spec、阶段计划和一次性验收报告不是默认发布物。必要的公开设计提案应单独评审，并明确标为提案。

## 架构决策的保存

ADR 默认作为内部资料维护，包含决策背景、备选方案、选择理由和后果。已接受决策需要改变时新增后继记录，保留原始背景及替代关系，不悄悄改写旧决策。

个人草案及本地归档可放在 `.local/docs/adr/`，禁止提交到公开仓库；团队长期记录应有受控的协作来源和访问权限。当前本地归档不替代团队知识库。需要公开说明某项取舍时，将影响外部使用者的理由和约束整理进相关正式手册，手册不得依赖内部 ADR 链接。

从导航或 `public-docs.txt` 移除文件不会使其变为私密资料；只要文件仍提交到公开 Git 仓库，就可以被访问。公开清单仅登记正式手册，内部 ADR 原文及模板不在 `docs/` 中维护。

本地忽略规则不是保密机制。已经进入 Git 历史、远端或发布包的内容不会因本次整理消失；若发现凭据或敏感信息，应另行处理。本次整理不改写 Git 历史。

## 维护检查

在仓库根目录执行：

```bash
uv run python -m tools.checks.check_docs
```

检查正式文档清单、仓库内链接和本地资料误入 Git 的情况。外部网站可达性与内容正确性由评审确认，不通过自动访问外部地址推断。
