# 文档维护与公开范围

`docs/` 维护随代码版本保存的贡献、安全、架构、迁移与发布约束。使用、部署和二次开发教程统一在 `hohu-admin-docs` 维护，本仓库旧教程只保留链接入口。同一正文不在两边复制。

## 收录标准

- 说明读者、适用范围、前提条件、操作步骤和已知限制。
- 使用仓库内可核对的命令、配置和接口；区分当前能力与尚未实现的方案。
- 一个主题只有一个维护来源，其他文档通过链接引用。API 字段细节优先由运行服务的 OpenAPI 提供。
- 示例不包含真实账号、令牌、业务数据、本机绝对路径或未验证的服务承诺。
- 功能变更时同步更新对应手册。长期架构取舍使用 ADR，不把执行清单或逐日验收日志作为 ADR。
- 新文档需加入 [文档入口](README.md) 和 `public-docs.txt`，并通过文档检查；通过链接检查不等于通过内容评审。

## 开发过程资料

草案、实现计划、调试笔记、测试报告、提示词、原型及临时附件保存在被忽略的 `.local/docs/`，按 `specs/`、`plans/`、`reports/` 等分类。此目录适合个人临时工作，不能成为团队唯一知识库。需要协作的方案通过 Issue、PR 或合适的团队资料渠道共享；必要架构决策、安全边界及贡献所需信息继续公开，稳定结论纳入正式手册或 ADR。

Spec-First 仍然有效：先写设计，再实现，再把已经落地的行为和必要决策整理进正式手册。原始 spec 不是默认发布物。必要的公开设计提案应单独评审，并明确标为提案。

本地忽略规则不是保密机制。已经进入 Git 历史、远端或发布包的内容不会因本次整理消失；若发现凭据或敏感信息，应另行处理。本次整理不改写 Git 历史。

## 维护检查

在仓库根目录执行：

```bash
uv run python -m tools.checks.check_docs
```

检查正式文档清单、仓库内链接和本地资料误入 Git 的情况。外部网站可达性与内容正确性由评审确认，不通过自动访问外部地址推断。

## 整理决策

1. **过程资料本地保存** — 保留设计上下文，同时控制公开文档范围。**反例**: 把全部草案移到仍被 Git 跟踪的 archive 目录，误以为不再公开。**回归**: 检查公开清单及忽略规则，确认归档文件未进入提交。
2. **按当前实现重写手册** — 删除未实现的插件分发、云市场拆分等部署承诺，保留真实限制。**反例**: 使用并不存在的配置指导生产部署。**回归**: 对照代码入口、配置定义和 CI 工作流核验文档。
3. **保留必要 ADR 和操作手册** — 公开范围由读者需要决定，不以缩减文件数代替质量。**反例**: 删除迁移及租户隔离说明，让使用者依赖聊天记录。**回归**: 从文档入口可找到部署、迁移、安全、贡献及扩展资料。

4. **产品手册统一维护在文档站** — 使用者与二次开发者有统一入口，代码仓库保留贡献与实现约束。**反例**: 两个仓库维护同一套上传或权限教程，代码更新后官网继续展示旧行为。**回归**: 旧教程为链接入口，站点构建、版本提示与双语检查通过。
