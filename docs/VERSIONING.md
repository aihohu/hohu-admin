# 产品版本、兼容性与分支规范

本规范适用于 HoHu 的后端、Web、App、Desktop、CLI 和文档。自采纳后用于需求归属、分支开发、兼容评审及发布验收；历史发布记录和标签保持原样。本文是跨仓库版本规则的唯一维护入口，各仓库保留执行细节并引用本文。当前产品状态统一查看 [Docs 更新说明](https://github.com/aihohu/hohu-admin-docs/blob/main/docs/zh/guide/reference/versions.md)；不可变产物事实以该页链接的正式 `release.json` 为准，工具及恢复命令分别见 [发布维护](RELEASE.md) 和 [清单手册](PRODUCT-RELEASE.md)。

规则生效不代表自动化已经完成。第 10 节列出当前工具限制；在补齐前必须满足对应的人工核对或使用前置条件，不能绕过已有安全、测试和发布门禁。

## 1. 产品版本与组件版本

| 对象 | 版本规则 | 示例与含义 |
| --- | --- | --- |
| 产品 / Backend / Web | Backend 与 Web 完整版本号一致，组合验收后形成一个产品版本 | 产品 `0.2.1` 包含 Backend `0.2.1` 和 Web `0.2.1` |
| App | 与目标产品采用相同 `major.minor` 兼容系列，补丁号独立递增 | App `0.2.3` 不要求后端也升级到 `0.2.3` |
| Desktop | 与目标产品采用相同 `major.minor` 兼容系列，补丁号独立递增 | Desktop `0.2.2` 可与 App 有不同补丁号 |
| CLI | 独立版本，声明所支持的产品范围和安装、升级能力 | CLI 的 `0.1.x` 不表示只支持产品 `0.1.x` |
| Docs | 按产品 `major.minor` 系列维护，说明补丁引入或修正的行为 | `0.2` 文档注明某功能从产品 `0.2.1` 开始可用 |

Backend 或 Web 即使没有业务变化，也要为同一次产品发布更新自身版本元数据、构建并形成同号产物。各仓库 Git SHA、构建摘要和发布时间可以不同；版本相同不能替代组合验收。组件仓库发布成功与产品发布完成是两个状态。

App/Desktop 尚未对外发布，首次正式发布目标统一为 `0.2.0`。现有占位包版本或本地标签不作为对外交付证明，不删除或覆盖历史引用。客户端可以晚于产品 `0.2.0` 发布；发布前要完成自身平台验收及配套验证，不因编号相同承诺所有端功能齐全。

### 版本递增与构建编号

- 产品补丁用于兼容修复、安全修复和运维修正；新增一组兼容的对外功能进入新的次版本。`0.x` 的破坏性公共契约变更进入次版本，`1.0` 起进入新的主版本，均须满足第 6 节的弃用与移除要求并说明升级路径。仍处于 `0.x` 不意味着可以静默破坏兼容性；已确认安全风险的例外按第 6.6 节处理。
- 客户端补丁用于同一系列内的修复、平台适配和兼容调整。客户端补齐该产品系列已有的业务能力，且不要求新增或改变服务端契约时，经范围与兼容评审后可以递增自身补丁号；例如产品 `0.2.0` 已有审批，App 可在 `0.2.1` 补齐该入口。需要新的产品能力或服务端契约时，重新确定目标产品系列、最低服务端版本和能力要求，不能仅靠递增补丁号规避兼容评审。
- CLI 按自身接口、模板和安装升级能力变更递增版本，不能从 CLI 版本推断产品版本。
- 客户端的商店构建号、平台 `versionCode` 等与展示版本分开管理，按各分发渠道的规则保持可升级顺序。重打包产生新的构建标识；已发布安装包不能原地替换。
- 测试构建采用可追溯的 SHA/运行编号，不占用正式稳定版本，不冒用尚未验收的正式标签。当前正式工作流只接受 `vMAJOR.MINOR.PATCH`；引入预发布版本前必须先扩展并验证工具链。

## 2. 需求必须归属版本

开始实现前，在内部设计、任务或 PR 中记录以下信息；公共手册只同步已交付行为及稳定规则，保存方式见 [文档维护](DOCUMENTATION.md)。

| 信息 | 要求 |
| --- | --- |
| 目标 | 目标产品版本；涉及客户端或 CLI 时，同时记录其组件版本和支持范围 |
| 范围 | 本版本交付的用户流程、明确不交付的部分，以及前置依赖 |
| 验收 | 成功、拒绝、失败恢复条件；涉及权限、迁移或协议时列出专项门禁 |
| 配套 | 受影响仓库、兼容客户端、文档及升级顺序 |
| 状态 | 区分设计完成、实现完成、集成验收通过、对用户开放、正式发布 |

架构阶段、原型通过和测试数量不能直接充当产品发布范围。可以按模块迁移，但已开放范围必须形成完整闭环，权限及数据隔离不能依赖尚未交付的后续阶段。

版本范围冻结后，新增需求需重新评估依赖、验收与交付成本，并更新同一范围记录；不能在稳定版本分支中悄悄加入下一版本的功能。没有确认目标版本时，可以继续调研和设计，不将新实现默认混入 `main`。

## 3. 分支模型

每个子项目仍是独立 Git 仓库。版本分支是该版本的集成分支，可从开发初期使用；不额外维护长期 `develop`。

| 分支 | 职责与规则 |
| --- | --- |
| `main` | 可发布的集成基线，接收完成验收的版本分支；日常功能与修复先进入对应版本分支 |
| `release/<version>` | 集成并冻结一个组件目标版本，如 `release/0.2.0`；Backend/Web 的目标必须一致 |
| `feat/<topic>` | 从目标版本分支创建，完成设计、实现和检查后向该版本分支提交 PR |
| `fix/<topic>` | 从目标版本分支创建，修复完成后回到同一版本分支；稳定版热修复见第 8 节 |

App/Desktop/CLI 的 `release/<version>` 使用其组件版本。Docs 内容跟随产品系列；需要随产品一起冻结时使用对应产品版本分支，单独文案修订按文档仓库的检查流程发布并记录文档提交。

默认维护一个功能版本分支、当前稳定系列的必要热修复，以及第 8 节中尚未结束的旧系列有限维护责任。不为每个历史补丁长期保留独立维护线；修复以该系列的新补丁交付。扩大维护范围前，先明确负责人、兼容矩阵及发布工具支持，不能只保留大量分支而没有验收责任。

正常流向：`feat/*` 或 `fix/*` → `release/<version>` → `main` → 正式发布。合并前应评审、完成适用 CI，并将 `main` 的修复纳入版本分支；合并后对实际发布 SHA 重新取得发布资格，分支名不构成验收证明。

首次引入规范时，CI 触发与分支门禁的配套改造可以通过独立治理 PR 先合入 `main`，不混入业务功能；验证完成后再用版本分支承接功能 PR。治理 PR 仍需遵循现有检查与授权规则。

开始任务先检查当前分支和未提交改动，保护已有工作。引入本规范不授权自动移动、拆分、暂存或提交现有改动；已有开发应先核对目标版本再归入分支。提交、推送、合并和发布沿用仓库既有授权规则，创建规范不表示授权执行这些操作。

## 4. 从候选版本到产品发布

1. **确定范围与前置就绪**：为 Backend/Web 建立同号目标，确认涉及的客户端、CLI、文档和升级限制；同时按 [测试指南](TESTING-GUIDELINES.md#完整用户操作验收) 冻结完整用户旅程，并按 [发布维护](RELEASE.md#前置检查与复核时点) 核查写者、凭据位置和网络。
2. **集成验收**：从首个可运行候选开始验证完整用户操作，在功能合入版本分支前完成适用旅程；在版本分支完成适用检查和组合验收，准备版本元数据、锁文件、变更说明、迁移与恢复说明。开发中的下一版本不得提前作为正式功能对外开放。
3. **冻结候选**：记录各仓库候选 SHA 和证据。若仍有修改，候选与相关验收记录随之更新；不能复用不匹配代码的结果。
4. **合并与发布资格**：按第 8、9 节先验证当前稳定系列的发布保障，再将完成验收的版本分支合入 `main`，确认最终 SHA，执行正式发布要求的检查。当前后端发布入口及其同运行恢复限制见 [发布维护](RELEASE.md)。
5. **产生组件产物**：通过各仓库受控发布流程创建标签、镜像或安装包。正式标签、构建摘要和已发布产物不可改写；代码变化后使用新版本。
6. **验证实际组合**：针对最终 Backend/Web 产物验证部署、支持的升级路径和关键用户流程，完成第 5 节的配套清单后才宣布该产品版本发布完成。
7. **更新可发现入口**：发布产品说明、兼容记录和文档入口；生产默认版本或稳定指针只能选择已经完成组合验收的产品。

两个仓库没有原子发布事务。若一端成功、另一端失败，产品状态仍为未完成：保留成功端的不可变产物，先判定失败端的远端写入状态，再选择恢复路径。代码必须变化、状态无法确认或原版本不能安全恢复时，两端共同选择新的产品版本；原版本保持未完成并保留原因及证据，不能以替换成功端标签解决不一致。

失败或取消不代表远端未写入。同一个 Git SHA、运行编号或正式 Git Tag，也不能证明重建后得到同一个镜像 digest。恢复前确认相关推送任务已终止、没有该版本的其他写入者，并核对本次涉及的目标仓库完整版本引用与已有产物证据；任务仍可能写入、查询失败或结果不一致时均按未知状态处理。

| 远端状态 | 允许的恢复 |
| --- | --- |
| 确认未发布正式镜像引用 | 可用于判断现场，但当前正式构建仍只允许原运行 attempt 1；失败后不能重跑构建或重用该版本，按发布维护记录原因并协调新产品版本 |
| 确认已发布且原 digest 可验证 | 只恢复同一 digest 的复制、验证和公告；不得重新构建并覆盖该完整版本标签，即使产品尚未宣布发布 |
| 上传结果未知、digest 无法确认或必须重建 | 停止该版本恢复，保留现场与原因，Backend/Web 共同选择新产品版本 |

当前工作流已在构建前认证查询正式版本引用，并以 `component-build.json` / `component-delivery.json` 绑定原运行、源码与 digest。正式构建仅允许原运行 attempt 1；只有原 build job 成功且原记录仍有效时，才在同一原运行恢复失败的 ACR/公告任务，始终复用原 digest。构建失败、记录缺失/过期、来源漂移或状态未知均停止；具体规则以 [发布维护](RELEASE.md#网页正式发布) 为准。恢复验收覆盖“远端接受上传但本地未收到确认”及“仅下游失败、不重建镜像”。

现有组件工作流会先交付组件 Release，但不推进系列或 `latest` 别名；组件公告不代表产品配套已经就绪。配套验证完成前，不引导用户将这组组件作为产品版本升级。生产部署应使用已验收清单中的明确版本和摘要，不能分别解析两个仓库的 `latest`。

## 5. 发布配套清单与证据

每个正式产品版本必须有一份机器可读的 `release.json`，作为后端对应 GitHub Release 的配套附件。先准备草案，补齐最终摘要及证据后发布；已发布清单不可覆写。已提供 v1 Schema、离线/在线校验器和不可覆盖上传器，执行方法统一见 [清单手册](PRODUCT-RELEASE.md)。清单准备、跨仓编排和报告内容复核仍由维护者负责；工具通过不能替代最终组合验收。

清单使用 `schema_version: 1`，字段、类型、必填、空值、枚举与跨字段校验已冻结，事实源为 [JSON Schema](../tools/ops/schemas/product-release-v1.schema.json) 与 [清单手册](PRODUCT-RELEASE.md)。下表说明语义，不另定义格式。格式不兼容变化时递增 `schema_version`，保留旧解释；CLI 尚不自动消费清单，不能将校验器能力归给 CLI。

| 内容 | 必须记录的事实 |
| --- | --- |
| 产品身份 | 产品完整版本、发布时间、清单格式版本 |
| Backend / Web | 仓库、同号标签、完整提交 SHA、实际产物地址与不可变 digest；多架构产物注明平台 |
| 升级边界 | 验证过的来源版本、数据库迁移目标、执行顺序、停机或兼容窗口、恢复限制 |
| CLI | 最低适用版本、实际测试版本及其可执行的安装/升级方式；未实现的能力不能写为支持 |
| App / Desktop | 已验证的组件版本、平台/构建标识、服务端范围及限制；未交付或未验证时明确标记，不用推测版本填充 |
| Docs | 产品系列、可访问的对应说明、实际文档提交 SHA；补丁特有行为需可追溯 |
| 验收证据 | 绑定实际 SHA/产物的检查、组合验收与升级恢复记录；列明未验证范围，不发布凭据和业务数据 |

清单草案、单元测试、隔离原型与生产可用资格各有含义，不能互相替代。正式发布说明面向用户描述可用功能、限制、配套版本和升级步骤；测试环境、配置与秘密不得直接进入公开附件。

同系列客户端后续发布时，为新组件版本发布独立、不可变的兼容证明，引用原产品清单和被测服务端产物。可更新兼容索引指向新证明，但不改写原清单来冒充该客户端在产品首发时已验收。证明纠错通过新的记录说明替代关系，保留原记录及安全撤回说明。

## 6. 兼容系列与权限契约

`major.minor` 相同表示目标兼容系列，不意味着所有补丁组合自动兼容。每次发布必须声明并验证可用组合，例如 App `0.2.3` 需要产品至少 `0.2.1`，不能只写“支持所有 `0.2.x`”。默认只承诺同系列内已声明的范围；跨系列支持必须单独验证并列入兼容矩阵。

兼容记录应覆盖服务端、客户端、平台、最低版本、能力限制和验证证据。可以使用已验证的连续范围；若某补丁不兼容或已因安全原因撤回，要明确排除，不能只写开放式最低版本。客户端功能可晚交付，界面应说明未支持能力，不能因产品号相同假定接口存在。

版本和能力协商只用于选择兼容行为，不能成为授权来源。后端仍按当前身份、租户、角色和字段策略授权；不兼容的敏感操作应拒绝并提示升级，不能退回返回全部字段或跳过租户条件的旧接口。

涉及字段缺失、掩码类型、只写字段、分页或错误契约变化时，必须验证支持范围内旧客户端的展示、筛选、提交与错误反馈。Backend/Web 同号也不能消除浏览器缓存、已打开页面和滚动部署产生的短暂混用；发布设计须选择并验证过渡兼容窗口，或明确安排停机、强制刷新与写入保护。

App/Desktop 更新前需确认目标包适用于用户连接的服务端、操作系统和发行渠道。更新失败或服务端不兼容时，应有明确的继续使用、升级服务端或停止不安全功能的路径；不能仅比较版本大小就宣称可安全升级。新增统一握手接口或协议版本号，应另行设计，本文不假定其已经存在。

### 6.1 兼容责任与生命周期

兼容责任按对象登记，期限不能互相替代：

| 对象 | 承诺范围与退出依据 |
| --- | --- |
| 旧产品系列维护 | 是否继续交付修复及何时停止维护，按第 8 节处理；停止维护不撤销新系列仍有效的接口兼容承诺 |
| 客户端与公共契约 | 已声明的客户端组合，以及正式 API、字段语义、配置项、CLI 参数和扩展契约；按兼容矩阵和下述弃用窗口退出 |
| 历史数据、升级与恢复 | 已承诺来源版本、持久格式、备份及恢复所需资料；通过迁移、归档或经过验证的中间版本升级路径退出 |
| 内部兼容实现 | 旧适配器、分支和解析器；没有公开契约、持久引用或恢复依赖且行为保持不变时，可经回归验证直接清理 |

公共能力依次处于“正常支持”“已弃用但在承诺范围内继续可用”“已移除”。弃用期间修复安全与兼容问题，新开发使用替代方案，不继续扩大旧契约。数据处理能力可以独立进入“仅迁移或只读解释”状态，不要求旧在线接口继续运行。正式发布前已明确声明的实验能力可以使用单独公告的生命周期，但仍须处理数据和安全依赖；不得事后把正式能力改称实验能力来缩短承诺。

### 6.2 公共弃用的版本与时间窗口

对正式承诺的公共能力，普通移除必须同时满足以下条件：

1. 在功能版本中公告弃用，说明受影响对象、替代方案、迁移步骤、限制和最早移除节点。替代方案须已可用；整体功能退役时，也须提供适用的数据迁出或受控停用方案。
2. 在公告弃用的功能系列及至少一个后续正式功能系列中继续履行原有兼容承诺；最早在其后的功能版本移除。按实际发布顺序计算，跳号不能缩短窗口，补丁和预发布不计为后续功能系列。系列内已有的明确组合限制仍适用。
3. 从弃用公告、承载弃用的正式版本、可执行迁移方案三者均可用的时点起，至少经过 **90 天**。记录起算日期及最早移除日期；已有更长的公开承诺继续有效。
4. 完成第 6.4 节移除验收。到达版本号或日期只表示可以评审移除，不表示自动取得删除资格。

例如某接口在 `0.2.0` 公告弃用，则在 `0.2.x`、`0.3.x` 的原承诺范围内保留，最早在 `0.4.0` 移除，且仍须满足 90 天及迁移验收。若 `0.4.0` 发布时未满窗口，应保留到之后满足条件的功能版本，不能在 `0.4.1` 中补做普通破坏性移除。此例不指定任何现有能力的实际退役版本。

产品 `0.x` 的普通破坏性移除只能进入次版本；`1.0` 起稳定公共契约的破坏性移除只能进入主版本，仍须满足上述窗口。`0.x` 跨入 `1.0` 不豁免已承诺的迁移期。CLI 按自身版本计算窗口，其他组件按该契约所属版本计算，不能用无关组件发版消耗窗口。已公告的移除节点可以延后，普通调整不得提前。

公共接口在新系列中保留，不自动证明某个旧 App/Desktop 或整套旧 Web 与新后端兼容。客户端仍按第 6 节已验证的组合使用；缩减既有支持范围须公告期限和更新路径。Web 过渡可按已声明的窗口验证强制刷新与写入保护；不得把刷新要求用于绕过独立的公共 API 承诺，也不得通过兼容分支放宽授权。

### 6.3 兼容条目登记与通知

新增兼容实现或决定弃用时，在对应内部设计及版本范围中登记条目；团队长期记录遵循 [文档维护](DOCUMENTATION.md)。维护者至少记录下列信息，不适用项注明理由，不能只写没有负责人和节点的 TODO：

| 信息 | 要求 |
| --- | --- |
| 身份与责任 | 稳定条目编号、兼容对象、代码或契约位置、负责人与决策状态 |
| 依赖与原因 | 涉及的产品/组件范围、客户端、扩展、租户资源、持久记录及恢复依赖 |
| 替代与迁移 | 替代能力、停止产生旧格式或新增旧引用的节点、调用方和存量迁移步骤 |
| 期限 | 弃用版本、公开公告及起算日期、最早移除版本/日期、计划执行版本；尚未公告时不开始计时，但须给出下一次复核版本或日期 |
| 验证与恢复 | 可检查的退出条件、所需测试、升级检查、回滚或恢复办法及不可逆限制 |
| 结果与延期 | 实际保留/移除结果；延期原因、新节点和负责人，更新对应公开信息 |

影响用户的弃用、停止维护及移除信息同步到适用的 Docs 系列和发布说明，提供迁移入口；有适用调用入口时提供清楚的弃用提示或升级检查。每次范围冻结核对本版新增和到期条目，明确移除、迁移或有期限的延期，不能无声滚存。实际移除时删除不再需要的适配分支及旧行为测试，保留迁移、拒绝旧用法和安全回归所需测试。

首次盘点已有兼容代码时，依据仍有效的公开承诺登记；代码存在时间、内部讨论、合并时间和本文采纳时间均不能替代正式弃用通知。自托管部署没有观测数据不代表无人使用，不以调用量为零作为唯一移除依据。

### 6.4 移除前的验收门

1. **契约与期限**：窗口已满足，受影响支持范围和迁移说明已公开，替代路径可用；受支持客户端完成组合验证，超出支持范围的旧请求有明确拒绝或升级提示，不能误解释后继续写入。
2. **调用与持久引用**：核查代码、配置、租户定制和扩展；涉及动作、事件、流程或 Skill 时，既检查在途工作，也检查尚未运行但仍启用的固定引用、待消费事件及等待人工处理的记录；停用后仍可恢复的资源也须纳入。相关引用须已迁移、排空，或转入不会被误恢复的受控停用路径并保留业务处理责任。
3. **数据与证据**：验证历史记录可正确读取、审计事实保留、必要幂等与未知结果保护持续成立。依赖尚未解除时保留最小解释能力或完成等价迁移，不通过删除证据、改写终态或重新执行业务来完成清理。
4. **升级与恢复**：对本次承诺的来源版本、备份、客户端及部署方式验证迁移和恢复。升级前检查能识别未处理依赖并停止不安全切换；没有自动检查时提供可重复的人工步骤，不能假定所有部署都已迁移。
5. **决定与验证**：记录负责人和适用验收证据，验证删除后的当前行为及旧用法拒绝路径。条件不满足时延期该移除并更新计划；其他独立工作可以继续，不能把整版发布当作强制删除理由。

### 6.5 数据兼容与内部实现的收敛

每个版本只承诺发布清单中已验证的升级来源。迁移链包含某旧 revision，不等于整套产品支持从对应版本直接升级；更旧版本可以先经过明确且已验证的中间版本。维护期结束不自动删除已发布迁移、历史产物、文档或恢复材料；变更迁移基线或压缩旧链须另行设计并验证受支持路径，遵循 [数据库迁移](DATABASE-MIGRATIONS.md)。

持久格式按“停止新增旧格式 → 迁移存量 → 验证读取与恢复 → 移除旧路径”处理。旧格式解释可集中到边界适配器、版本化迁移器或只读工具，使主业务处理统一模型。保留的工具也须明确输入边界、依赖、使用权限和安全限制，不得成为绕过当前授权的入口。

历史 AI 执行、确认、回执及审计尤其不能按客户端退役日期直接清除：结果未知仍须保持未知和防重执行约束；旧 owner 或载荷仅改标识不能成为新协议的成功证据。退出旧解析器前，应迁移可证明等价的事实，对其余未决记录保留有责任主体的核对和隔离路径；具体行为遵循 [AI 安全](AI-SECURITY.md)。正常数据保留与删除政策独立执行，移除兼容代码本身不授权删除业务或审计数据。

纯内部实现没有外部契约、持久引用、支持范围内旧二进制或恢复依赖时，可在适当的开发切片中直接清理，保持公共行为并完成相关回归；不强制等待公共弃用窗口。存在上述任一依赖时，仍须登记并按对应退出条件处理。

### 6.6 安全例外

已确认的越权、数据泄露、数据损坏等风险使旧行为无法安全保留时，维护者可以在安全补丁中提前限制或禁用受影响能力。须记录风险依据、影响版本、必要的最小变更、迁移或缓解措施以及验收结果，并按 [安全说明](SECURITY.md) 的披露流程同步公告和兼容矩阵；敏感细节可按协调披露时点公开。

安全例外不用于普通重构或降低维护成本，也不授权恢复旧权限、删除未决事实或改写历史产物。需要提前停止某种部署方式时，给出安全的停止/升级路径，不能默默回退到不安全实现。

## 7. CLI 与文档交付

CLI 每次发布说明支持哪些产品版本，以及创建、安装、部署和升级分别支持什么。用户选择产品版本时，应能追溯到配套清单中的仓库提交或产物摘要；不得用最新源码替代用户选择的稳定版本。固定标签后的 detached HEAD、旧项目检测、镜像选择和迁移顺序都属于版本选择能力的验收范围。

在 CLI 尚不支持上述选择前，明确记录它实际取得的分支或镜像，并由维护者核对和固定来源；不能提供不存在的命令参数，也不能把从 `main` 创建的项目标为稳定版本的可复现安装。当前创建和部署能力应分别评估，不能因其中一种可固定镜像就推定另一种已经支持源码版本选择。人工核验必须绑定实际迁移和运行的产物，仅提前拉取并检查版本标签不足以保证后续部署仍使用同一镜像。

现有容器部署可采用以下人工过渡流程，首次使用前应在隔离环境验证：

1. 按配套清单在目标主机准备并核验目标平台的镜像，记录实际仓库、manifest digest 与完整 `仓库@sha256:摘要` 引用，确保该引用已存在于本地。
2. 在部署目录 `.hohu/deploy/docker-compose.override.yml` 中，给 `db-migrator`、`hohu-admin-api`、`hohu-admin-scheduler` 指定同一个已核验的后端完整引用，给 `hohu-admin-web` 指定已核验的 Web 完整引用；这四个服务分别设置 `pull_policy: never`。纳入清单的其他镜像也须固定。不要把 digest 直接填进 `API_IMAGE` / `WEB_IMAGE`，当前模板还会追加版本标签。
3. 按 CLI 实际的 Compose 文件顺序、环境配置及 `migrate` profile 检查合并后的镜像引用、平台和拉取策略，再执行迁移与启动；缺失或不匹配立即停止。核验后不得重新标记或替换所选本地镜像，不切换到未核验的镜像源，也不回退到 `latest`。

当前 CLI 会加载用户 override，`pull_policy: never` 跳过其预拉取，迁移与启动也使用禁止拉取的方式；但它不会替代人工校验发布清单或目标平台。完整 digest 引用不会自动映射到另一个镜像仓库，切换仓库需重新准备并核验该仓库的完整引用。这个过渡流程不代表 CLI 已实现产品版本选择或清单校验。

Docs 的导航、页面说明与产品系列应一致。未来系列的未发布功能不能覆盖当前稳定系列的使用方法；补丁差异注明从哪个版本开始可用，安全限制同步更新。Doc 包自身 `package.json` 版本不是产品兼容声明。

站点尚未提供多版本路径或切换器时，必须显示所对应的产品系列/版本状态，并保留可追溯的旧版本说明。在第二个需要同时支持的产品系列公开发布前，落实可访问的系列文档路径或归档入口并验证链接；仅保留 Git 分支不能替代面向用户的版本文档入口。

## 8. 热修复、支持与恢复

默认正常维护当前稳定产品系列，正在开发的下一系列不视为已发布支持。下一系列正式发布、适用升级路径可用、上一系列停止维护（EOL）公告公开三者均满足后，上一系列进入 **90 天有限维护期**，主要交付安全、数据完整性和阻断升级问题的修复。公告记录起算日期、停止维护日期、维护责任人、支持的升级路径及适用范围；尚无公告不启动倒计时。已有更长期限继续有效，不因快速发布更多系列而提前结束已公告窗口。

有限维护到期后停止为该系列提供常规补丁，保留可追溯的产物、文档和升级说明；更长维护或 LTS 必须另行明确期限、责任及发布保障，不默认承诺。系列维护期与第 6 节公共契约弃用期分别计算，EOL 不取消新版本中的有效接口承诺，不自动扩大或撤销某个客户端组合，也不授权删除历史数据。

维护范围、期限和安全撤回通过公开支持状态索引及公告维护，保留变更历史；已发布的 `release.json` 只记录当次不可变事实，不为后来的 EOL 或兼容调整覆写。每次发布检查两个窗口中的适用责任；本规范不为任何既有系列补设已经过去的 EOL 日期。

当前稳定版修复从其发布基线建立新的补丁版本分支，再建立 `fix/*` 短分支。Backend/Web 仍发布同号补丁，即使仅一端需要修复。热修复完成后同步回灌正在开发的版本分支并复核冲突、迁移和测试，避免下一版本重新引入问题。

只在 `main` 仍可承接该稳定系列时使用现有默认分支正式发布流程。下一系列合入 `main` 前，必须补齐并验证当前仍受支持系列的独立受控发布路径，能够从其发布基线交付 Backend/Web 同号热修复并执行相同的适用安全与发布检查。该路径未就绪时，下一系列保留在版本分支，不能先合并、等紧急修复出现后再改造工具。

下一系列合入 `main` 但正式发布或最终组合验收失败时，原稳定系列仍受支持；合并不是结束维护的依据。验收应演练这个窗口内的旧系列热修复。不能将 `main` 回退、移标签或绕过分支保护来模拟发布支持。

客户端单独修复仅递增自身补丁，除非同时需要服务端契约变化。CLI 单独修复仅递增 CLI，并重新验证受影响产品范围。文案修正可独立发布 Docs，但要保留版本归属和文档提交记录。

恢复必须考虑数据库、持久文件、构建、资源版本和密钥。旧镜像可用不表示数据库可逆；每次涉及数据或权限迁移的发布都需写清支持的恢复路径及不可逆限制，遵循 [数据库迁移](DATABASE-MIGRATIONS.md) 和 [发布维护](RELEASE.md)。

## 9. 合并与发布门禁

| 时点 | 必须满足 |
| --- | --- |
| 功能合入版本分支 | 目标版本与范围明确；设计/回归/文档齐全；新增兼容或弃用条目已登记；首个可运行候选已完成适用的完整用户旅程；适用测试、类型和覆盖率检查通过；权限与租户边界不因分期而削弱 |
| 版本合入 `main` | 范围冻结并处理本版到期兼容条目；依赖和升级路径明确，计划移除已通过第 6.4 节验收；涉及仓库的候选组合通过验收；未交付功能有准确限制；下一系列合入前，当前受支持系列的独立热修复发布路径已验证 |
| 组件正式发布 | 写者/凭据/网络前置检查有效，正式构建前已按实际交付客户端复核；最终 SHA 与版本元数据一致；当前仓库完整发布门禁通过；产物不可变并可追溯；失败恢复已判定远端写入状态，不以重建覆盖已发布产物 |
| 产品宣布发布 | Backend/Web 同号且最终产物组合通过；配套清单完成；可用 CLI 路径、兼容记录、用户文档和恢复说明齐备；适用的弃用/移除及 EOL 信息已公开，期限按实际可用时点起算 |

纯文档修改按文档检查流程执行；行为、权限、迁移或工具链变化按对应测试规范执行。任何未验证的平台、版本范围或恢复路径必须如实记录；属于本次承诺范围的必要证据缺失时，不能以备注替代验收。

## 10. 当前工具边界与落地前提

本节记录采纳本规范时核查到的约束；相关工具完成改造和验证后更新，不能把下表当作长期豁免。

| 能力 | 当前边界 | 使用前提 |
| --- | --- | --- |
| 版本分支 CI | Backend/Web CI 配置保留原默认分支及 `workflow_call`，覆盖 `release/*` 的 push 与以其为目标的 PR；后端文档检查覆盖同一分支范围，普通检查 token 限定只读 | 配置不证明远端保护已生效；承接功能 PR 前，实际核验触发、required checks 与分支保护，并验证必需检查失败会阻止合入 |
| 正式 Backend/Web 发布 | 两仓独立执行；后端正式和测试镜像入口限定默认分支，稳定版本格式固定 | 继续按现有入口发布；版本分支验收需先运行适用检查，不把发布镜像入口当作任意分支构建器 |
| 发布失败恢复 | 已有认证引用预检、原 build 记录和交付读回；正式 build 拒绝 attempt > 1 | 仅原 build 成功、记录有效且来源一致时，在原运行恢复下游；未知/冲突/记录失效停止，见发布维护 |
| 稳定系列热修复 | 当前默认分支入口不能发布已不在 `main` 上的旧系列 | 下一系列合入 `main` 前验证当前稳定系列的独立受控发布路径，并覆盖新系列发布失败期间的热修复 |
| 产品配套清单 | 已有 v1 Schema、离线/在线核验及不可覆盖上传；没有通用生成器或跨仓原子编排，不推进系列/latest | 按清单手册准备和复核资料；最终产物验收后核验、上传并读回原字节；部署固定 digest |
| CLI 产品选择 | 当前源码创建以 `main` 为来源；容器部署不会自动核验配套清单 | 固定来源能力另行实现并验证；人工容器过渡按第 7 节绑定全部迁移/运行服务的已核验引用并禁止重拉，不能只提前检查标签 |
| App/Desktop | 首次正式发布及配套矩阵尚未完成；桌面更新器不能被视为已有服务端兼容门禁 | 首发前明确展示版本、平台构建号、渠道与更新策略，验证服务端不兼容路径；兼容门禁未具备时，不启用未经验证的自动升级路径 |
| Docs 多系列 | 当前站点不具备产品版本切换能力 | 发布第二个受支持系列前落实系列路径或归档入口；此后文档发布不得相互覆盖 |
| 兼容生命周期执行 | 本规范定义维护规则，不代表已交付统一弃用扫描、依赖盘点、到期阻断或客户端强制升级工具 | 维护者按第 6、8、9 节逐项登记、通知和验证；所需工具另行设计，缺少自动化不豁免移除条件 |

分支 CI、版本选择、客户端更新和清单自动化各自需要独立设计与验收，不必为了发布第一个治理后的补丁提前建成完整市场或发布平台。手工发布配套清单是允许的过渡执行方式，权限隔离、固定产物、组合验收和恢复约束不能延期。
